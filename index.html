01

Multi-agent publishing workflow

In production for 6 months

7–10 articles a week, with hands-on time cut from 4+ hours to about 30 minutes per two articlesReviews, news, and evergreen content, produced by a team of agents for the last six months.

The problem

Every pair of articles meant researching topics, writing a brief, drafting, editing, and preparing images by hand. That took at least four hours.

What I built

A team of specialist agents, each with one job, that hands work along a fixed path and stops at two points for a human decision.

Research agentFinds candidate topics on a schedule
→
Human decisionI choose the topic
→
Editor agentReads search data, writes the SEO brief
→
Writer agentDrafts the article into WordPress
→
Human decisionI edit and publish

The workflow path. Shaded steps are the points where nothing moves until a person decides.

  • The editor agent checks Google Search Console data and existing coverage before it writes a brief, so new articles don't compete with old ones.
  • Fact-checking is built into both the editor and the writer stages.
  • A separate SEO agent proposes weekly improvements to older articles.
  • I run all of it from Slack: paste links, approve a brief, and come back to a finished draft.

How it's controlled

  • Agents can create drafts only. A person selects every topic and reviews every article before it goes live.
  • Changes to live pages go through a separate, permission-isolated service. The agents never hold the site's credentials, and each change needs approval of its exact content.

Built with

Hermes agent framework, DeepSeek, Google Search Console API, WordPress REST API, Slack, scheduled jobs, and a Kanban task queue.

Limits: The time saving is my own measurement of hands-on editing and image work. The site isn't named here, but I can demonstrate the workflow live.

02

Agent hub and workflow control

In productionSoftware workflow in development

The problem

Once several agents share projects, the risk changes. An agent that acts on half-loaded data, on an instruction that changed after it was approved, or on a setting that only partly applied can do damage quietly.

What I built

  • A self-hosted Linux server that connects agents and projects through Slack for conversation, Linear for project tasks, and Tailscale for private access.
  • Separate director, builder, reviewer, and publisher roles, with a model chosen for each kind of task.
  • Permissions set in configuration. An agent's role decides what it may touch, not what its prompt says.
  • Approved tasks are frozen with a fingerprint, so any later change to the task is detected.

What happens when something goes wrong

If this happensThe system does this
Project data only partly loadsThe update is rejected and the last complete copy stays in place.
A task changes after it was approvedThe earlier approval no longer applies. The new version must be approved again.
A schedule change fails halfwayEvery timer is restored to exactly how it was before.
A command reports success but nothing changedIt is treated as a failure and rolled back.

105 automated testscover input validation, tasks that change after approval, schedule changes, and rollback.

Built with

Ubuntu server, Python, Hermes agent profiles, Slack, Linear, Tailscale, and systemd timers.

Limits: The tests run offline against simulated services. The hub runs content work today; the full build-and-review workflow for software projects is still being built. The source is private, and I can walk through it on a call.

03

Editorial QA tool

In use4 versions over 2 yearsAgentic version in development

The problem

Checking a long article against its brief, the house style, and its own internal consistency takes an editor a long time. An AI reviewer that invents problems makes that worse, because every false flag has to be checked by hand.

What I built

  • A Python tool that reads the article and its SEO brief, then reports missing sections and missed keyword targets.
  • Grammar and readability checks that run on fixed rules, with a dictionary of industry terms so jargon isn't flagged as an error.
  • A model-based check that finds statements in the article that contradict each other.
  • I built it on my own time. It was later accepted for use at 22Bet Partners.

How it's controlled

These controls belong to the newest version, which is still in development.

  • Every model-based finding must quote the article word for word. If the quote can't be found in the text, the finding is thrown away before anyone sees it.
  • Before a correction is applied, the tool checks that the passage still reads as it did. If the text has moved on, the edit is skipped and reported.
  • When two corrections touch the same words, the conflict is detected and both are not applied blindly.
  • Suggestions are kept separate from accepted revisions.

Built with

Python, Flask, OpenAI API, LanguageTool, and sentence embeddings for matching brief headings to article sections.

Limits: If a model call fails, the tool returns no findings for that check, so an empty report isn't proof of a clean article. Brief formats vary widely and each new format needs testing.

05

MiseMind: a culinary knowledge assistant

Personal application

The problem

A general chatbot answers cooking questions from nowhere in particular. I wanted answers and recipe analysis grounded in a specific reference library, with the source visible.

What I built

  • A retrieval-augmented app that reads and cleans reference documents, splits them into small searchable passages linked to their larger sections, and retrieves the most relevant ones for each question.
  • Structured recipe parsing and analysis, with the source passages shown beside each explanation so it can be checked.
  • A check that flags long word-for-word overlaps with the source material.

Built with

Python, Streamlit, SQLite, and vector search.

Limits: I haven't measured retrieval accuracy formally. The reference library is private and not included.
